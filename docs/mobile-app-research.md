# 移动端 App 化预研（APK 方案）

> 状态：**留档，暂不实施**（2026-11-06 预研，用户决定搁置）。
> 结论：可行且有三级路径；若启动，按「PWA → WebView 壳 APK」两步走，不走原生重写。

## 背景

PiNasDeck 网页端已适配手机（v0.3.x 响应式 + v0.5.1 顶栏），但浏览器形态的固有短板：
切后台即断连、无图标级入口、无通知栏提醒。目标是评估做成 APK 联通 NAS 的可行性。

## 路线对比

### 路线 0：PWA（不写 APK，约半天）
- 加 `manifest.json` + 图标 + `theme-color` →「添加到主屏幕」得全屏类 App 体验
- 得到：图标、全屏、独立窗口、localStorage 延续登录态
- 得不到：后台常驻（锁屏/切走后 WebSocket 被系统杀）、通知栏推送

### 路线 1：WebView 壳 APK（推荐主力，1~2 天）
- 单 Activity WebView 加载 `http://<NAS>:8080` + 图标/启动页/首启输地址
- 得到：真 APK 体验；**前台服务保活 WebSocket → 通知栏推送**（任务完成/微信回复/定时任务，锁屏可见）——这是浏览器给不了的核心增量；文件选择器/拍照直通（onShowFileChooser，含目录选择）
- 关键技术点：
  - NAS 为 `http://` 明文 → 网络安全配置仅放行内网（usesCleartextTraffic/NetworkSecurityConfig）
  - 登录态 = WebView localStorage，天然延续网页端 token
  - 国内手机后台管控凶：**前台服务 + 常驻通知**是唯一可靠保活；FCM 不可用，厂商推送 SDK 工作量翻倍收益低（且已有微信 bridge 作为通知通道，边际价值中等）
- 分发：自签 APK 侧载（自用无需商店；局域网 http 也无法过 Play 审核）

### 路线 2：原生重写（Kotlin/Flutter，1~2 个月）
- 聊天流式/Markdown/文件树/标签页/定时任务全部重写 + 双份维护
- 除产品化/上架外不值得——核心功能全在服务端

## 建议（若启动）

1. **先 PWA**（半天）：立刻获得图标+全屏，验证真实需求强度
2. **再 WebView 壳 APK**（1~2 天）：核心增量 = 前台服务保活 + 通知栏；壳内加载 PWA，前端零改动
3. 不碰原生重写

## 落地时的验证清单（启动时用）

- [ ] WebView 文件上传（含 webkitdirectory 文件夹）与拍照回调可用
- [ ] 明文 HTTP 仅对内网放行，外网域名仍拒绝
- [ ] 杀进程重启后 localStorage 登录态存活
- [ ] 前台服务下锁屏能收到「任务完成」通知（MIUI/ColorOS 各测一台）
- [ ] 与网页端并行使用互不干扰（同一 token 多端）
